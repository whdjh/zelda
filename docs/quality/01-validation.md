# 품질 검증 계획 — 콘텐츠·사용성·코드

## 품질 기준은 세 종류

1. **콘텐츠 사실성**: 실제 리메이크에서도 가능한 루트인가?
2. **사용자 효용**: 일반 사용자에게 더 쉽고 빠른가? 힌트가 재미를 보존하는가?
3. **소프트웨어 안정성**: 기록이 보존되고 모바일에서 사용 가능한가?

## 게임 플레이 검증

| 검증할 항목 | 방법 | 증거 |
| --- | --- | --- |
| 필수 진행 조건 | 실제 스위치 2에서 해당 상태 재현 | 플레이 로그·조건 체크 |
| 지름길 가능 여부 | 같은 출발 상태에서 재현 | 실패/성공 기록 |
| 추천 경유 가치 | 경유/생략 두 루트 비교 | 준비·이동·전투 시간과 실패 횟수 |
| 퍼즐 힌트 적절성 | 공략 모르는 테스터가 단계별 공개 | 너무 노골적인 힌트/무의미한 힌트 피드백 |
| 명칭·조작 | 게임 내 한글 UI·설정과 대조 | 표기/버전 메모 |

'한 번 내 플레이에서 빨랐다'만으로 전체 인구 최적임을 주장하지 않는다. 루트별 조건과 조작 난도, 실패 위험을 함께 기록.

## UX 테스트 시나리오

- 초보 이용자가 처음 켜고 '지금 할 일'을 찾는 데 걸린 시간.
- 스포일러를 보기 싫은 사용자가 힌트만 보고 이동할 수 있는지.
- 임의로 먼저 지나간 역이 있을 때 현재 위치를 수정할 수 있는지.
- 폰 브라우저 종료 → 재오픈 후 데이터 보존.
- 같은 사용자가 홈 화면 설치/PWA와 브라우저에서 저장 공간 차이를 이해하는지.

## 코드 테스트

현재 실행 명령과 실제 수행 결과는 [개발 검증](../development/01-local-setup.md), [상태 기록](../development/02-project-status.md)에서 관리한다. 아래 전체 제품 검증 항목이 초기 골격만으로 완료된 것은 아니다.

- RouteStop 정렬·선행 조건 함수 유닛 테스트.
- 완료/되돌리기/보유 조건 수정 → 규칙 기반 추천 재계산, 선행 조건 충돌 및 힌트 공개/백업·복원 통합 테스트.
- 스키마 마이그레이션·잘못된 JSON·누락된 ID 검사.
- 주요 모바일 viewport에서 레이아웃/탭 크기, 스크린리더 라벨·키보드.
- `prefers-reduced-motion`, 네트워크 끊김, 저장 차단 모드.
- 스포일러 `strict/default/full` 및 검색 메타·DOM·스크린리더에서 미래 구간/퍼즐 해법의 의도치 않은 노출이 없는지 검수.
- CSS는 SEED 토큰 우선, 중복된 색/간격 스케일이나 불필요한 상태 관리 라이브러리가 추가되지 않았는지 정적 리뷰.
- 색 대비 자동 검사 + 수동 확인.
- Supabase 로그인·콜백/쿠키·로그아웃, 비로그인 Action 거부, 사용자 A/B RLS 격리, 같은 계정 동시 revision 변경 충돌을 실제 DB에서 검증한다. 외부 연결 없는 빌드 통과와 구분한다.

## 출시 승인 게이트

- [ ] 메인 루트의 모든 공개 역/선행 조건이 출처와 실제 버전 관점에서 검토됨.
- [ ] 모든 사용자 공개 퍼즐의 마지막 해법이 재현되거나 미검증 상태가 명시됨.
- [ ] 첫 화면/노선도/힌트 공개/저장·복원 플로우에서 차단 버그 없음.
- [ ] 필수 사용자 여정 모바일 실기기 테스트 통과.
- [ ] 서드파티 미디어 권리 확인, 비공식 표기 게시.
- [ ] GA4와 Search Console에서 필수 이벤트/색인 확인(법적 고지 포함).

## 기준을 낮추지 않는 방법

공략 취재가 개발보다 늦어지면 디자인을 부풀리거나 미검증 텍스트를 AI로 채우지 않는다. **콘텐츠 검증의 진척을 공시하는 베타**는 가능하지만 '전체 검증된 하이패스'라고 표기할 수 없다.
